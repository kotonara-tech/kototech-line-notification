# docs-professional

ドキュメントは「読む人が次の行動を決められる」ために書く。長さより、**正確さ・探しやすさ・最新であること**を優先する。

## 基本原則

1. **読み手と目的を先に決める**。設計書は「実装者が迷わない」、運用ルールは「手順どおりに動ける」、README は「全体像と入口が分かる」
2. **結論と理由をセットで書く**。決定は「何を決めたか」だけでなく「なぜか」(代替案を捨てた理由)を残す。後から「なぜこうなっているのか」を再調査しなくて済む
3. **1 つの事実は 1 か所に書く**。複数箇所に書くと、片方だけ古くなる。別の文書の内容は、コピーせずリンクする
4. **コードと食い違わせない**。設計やコードを変えたら、同じ変更でドキュメントも更新する。更新を後回しにした時点で、ドキュメントは嘘になり始める
5. **未確定を確定のように書かない**。決まっていないことは「未決」として明示し、仮定には「仮」「案」と書く。推測を事実として書かない
6. **短く、構造を揃える**。見出しの順序・用語・表の列を、文書間で揃える

## このプロジェクトのドキュメント構成

```
README.md                     # プロジェクトの概要(入口)
CLAUDE.md                     # AI(Claude Code)向けの設定・方針
docs/
├── README.md                 # docs の説明(100 行まで)
├── engineering/              # 開発に必要な設計
│   ├── 00-openquestion.md    # 未決事項と決定の記録
│   ├── 01-overview.md        # 概要
│   ├── 02-infra.md           # インフラ
│   ├── 03-backend.md         # バックエンド
│   ├── 04-timetable-sheet.md # 工程表(スプレッドシート)の形式
│   └── 04-timetable-sample.csv # 工程表のサンプル
├── operations/               # 運用ルール(GitHub の利用フローなど)
├── infra/                    # インフラ構成図(architecture.png)
└── mocks/                    # Flex Message などの HTML モック(全シナリオ)
```

- 設計書は `docs/engineering/` に **`NN-名前.md`**(2 桁の通し番号 + 英小文字のケバブケース)で置く。`00` は常に未決事項と決定
- 運用ルールは `docs/operations/` に、同じ番号付けで置く
- 新しい文書を足したら、`docs/README.md` の構成表に追記する(`docs/README.md` は**100 行まで**)
- ドキュメントの言語は**日本語**。文体は「〜する」「〜である」の常体で統一する。コード・識別子・コマンド・ファイル名は英語のまま、バッククォートで囲む

## 設計変更のたびにやること

設計の変更は、ドキュメントの変更を伴う。次の順に確認する。

1. **どの文書が正本か**を決める(概要は `01`、インフラは `02`、バックエンドは `03`、運用は `operations/`)
2. 正本を更新し、**他の文書は要約とリンクだけ**にする(重複を更新しない)
3. `00-openquestion.md` を更新する
   - 新しく出た疑問は「未決」に追加(ID は欠番を再利用せず、続きの番号を振る)
   - 決まったことは「決定」に移し、**理由**を書く。解決した「未決」は削除する
   - 決定が覆ったら、古い決定を消さずに**更新**し、変更の理由(「旧: …」)を残す
4. 関連する図(Mermaid、`architecture.png`)を更新する。**文章だけ直して図が古いまま**になりやすい
5. `README.md` / `CLAUDE.md` / `docs/README.md` に影響するか確認する(ディレクトリ構成、方針、コマンド)
6. 用語を grep して、古い表現が残っていないか確認する(例: 廃止した環境変数名、削除したパス)

## 未決事項と決定の記録(`00-openquestion.md`)

| 項目 | 書き方 |
| --- | --- |
| 未決(`Q<n>`) | 質問は 1 文で、答えが選べる形にする。「備考」に、判断に必要な情報(選択肢、影響、関連する ID)を書く |
| 決定(`D<n>`) | 決定内容と**理由**を 1 行ずつ。別の文書に詳細があればリンクする |

- ID は一度振ったら変えない(他の文書から参照されるため)。参照するときは `Q9`、`D13` のように書く
- 決定した内容は、正本の文書(`01`〜`03`)にも反映する。`00` だけに書いて終わりにしない

## 書き方のコツ

### 構造

- 結論を先に書き、詳細を後ろに置く。見出しだけ追えば全体が分かるようにする
- 見出しは階層を飛ばさない(`##` の次に `####` を使わない)。深くなったら文書を分ける
- 列挙は表にする。「項目 × 属性」の比較、設定値の一覧、権限の対応は特に表が向く。手順は番号付きリスト、並列の項目は箇条書き
- 1 つの文は 1 つのことだけを言う。長い文は分ける
- 「など」「いろいろ」「適宜」を避け、具体的に書く。曖昧なまま残すときは「未決」にする

### 数値・名前・時間

- 固有の名前、パス、コマンド、環境変数、ID は**バッククォート**で囲む
- 数値には単位を付ける(`300 秒`、`10 世代`)。上限・既定値は、どちらか分かるように書く
- 「最近」「今」「現在」のような**相対的な時間表現**は、後から意味が変わる。日付を書くか、状態(「MVP では」「フェーズ 1 では」)で書く
- 変わりやすい外部サービスの仕様(料金、無料枠、クォータ、API の挙動)は、「公式で確認」と書き、確認していない数値を断定しない

### 手順書(運用ドキュメント)

- 手順は番号付きで、1 手順 1 アクションにする。実行するコマンドはコードブロックで示す
- 前提(必要な権限、事前の準備)を手順の前に書く
- 失敗しやすい点・戻し方(ロールバック)を書く
- **一度きりの手順**(初回セットアップ)と**繰り返す手順**(日常の運用)を分ける

### 図

- 構造や流れの図は **Mermaid** をまず検討する。テキストなので、差分でレビューでき、更新の手間が小さい
- 見た目が重要な構成図は画像(`docs/infra/architecture.png`)にする。画像は、手で描かずに、生成スクリプト(`docs/infra/generate_architecture.py`)の座標とラベルを直して再生成する。更新したら、**必ず目で見て確認**する(文字のはみ出し、矢印がラベルを貫通していないか、古い表記の残り)
- 図の中の用語は、本文と**同じ表記**にする
- 図だけで済ませず、図が何を示すかを 1〜2 文で説明する

### リンク

- 別の文書へは**相対パス**のリンクにする(`[02-infra.md](02-infra.md)`、`../operations/01-operations.md`)
- リンク先の見出しを変えたら、参照元も直す
- 外部リンクは、変わりにくい公式の入口を選ぶ

## README / CLAUDE.md

- `README.md`: 目的、構成(ディレクトリ表)、概要、ステータス。詳細はリンクに任せ、**30 秒で全体が分かる**長さにする
- `docs/README.md`: `docs/` の構成表とルールのみ。100 行まで
- `CLAUDE.md`: AI への指示。**守ってほしい方針とディレクトリ**を簡潔に。設計の詳細は書かず、正本の文書へリンクする。方針が変わったら必ず更新する

## HTML モック(`docs/mocks/`)

Flex Message の見た目と、実際に届く表示を、**全シナリオ**分まとめる。

- 1 ファイルで完結する HTML にする(外部の CSS・JS・CDN に依存しない。オフラインで開ける)
- LINE のトーク画面の幅(スマートフォン幅)で表示し、吹き出し・送信者名・時刻を再現して、「実際にどう見えるか」を伝える
- シナリオごとに見出しを付け、**何が起きたときにこの通知が届くか**(条件)を併記する
- 各メッセージに、送信する **Flex Message の JSON** を併記する(開閉できるようにしてよい)。見た目と送信内容を、同じ場所で突き合わせられるようにする
- 通知の種類・文面を変えたら、モックも同じ変更で更新する(`CLAUDE.md` の方針)
- 実在の個人情報・実在のイベント参加者名を入れない。ダミーの値を使う

- [ ] 未確定のことを、確定のように書いていないか
- [ ] 同じ事実を、複数の文書に重ねて書いていないか(リンクで済ませられないか)
- [ ] 図・表・リンクは最新で、本文と表記が揃っているか
- [ ] `00-openquestion.md` の未決・決定を更新したか
- [ ] `docs/README.md`(100 行以内)・`README.md`・`CLAUDE.md` への影響を確認したか
- [ ] 廃止した用語・パスが残っていないか(grep で確認したか)
