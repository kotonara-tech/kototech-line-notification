# 04. リリースゲート

`develop` → `main` のリリース PR に、マイルストーンの Issue が終わっているかを、コメントで示す仕組みと、そのために守る Issue の使い方をまとめる。ブランチの役割とマージ方法は [01-operations.md](01-operations.md) が正本で、リリースの手順は [03-release.md](03-release.md) にある。

**検証の状態**: workflow は、偽の `gh` を使ったローカルの実行(場面ごとの出力と終了コード)と、`gh` の読み取りで確かめた。次は、GitHub 上では未確認。最初のリリース PR で確かめ、食い違いを直す。

- 実際の PR での実行。`GITHUB_TOKEN`(`pull-requests: write` と `issues: read` だけ)での、Issue の読み取りとコメントの作成・更新
- ステップのタイムアウトや想定外の失敗が、`continue-on-error` でジョブの成功になること。取り消された実行の、チェック欄での見え方
- エスケープした Markdown の表示、`@` の後ろのゼロ幅スペースで通知が飛ばないこと

## リリースゲートの目的と動き

マイルストーン(2 週ごと)に含まれる Issue が終わっているかを、リリース PR から確認できるようにする。ゲートは**情報の提示だけ**で、リリースをブロックしない(失敗させない。必須のステータスチェックにしない)。

| 項目 | 内容 |
| --- | --- |
| workflow | `.github/workflows/release-gate.yml`(`ci.yml` とは別) |
| 起動 | `main` 宛ての `pull_request`(`opened` / `reopened` / `synchronize` / `edited` / `milestoned` / `demilestoned`) |
| 対象のマイルストーン | PR に設定されたマイルストーン。未設定のときは、コメントに「マイルストーンが未設定」と書く |
| 対象の Issue | そのマイルストーンの Issue(PR は含まない)のうち、**子 Issue を持つ親 Issue を除いたもの**。子 Issue と、親も子も持たない単独の Issue |
| 終わっている | クローズ済み。閉じた理由(完了 / 実施せず / 重複)は区別しない。区別するかは未決(「未決」の節) |
| コメント | 対象の Issue の一覧(番号・タイトル・領域ラベル・済 / 未)と、済の数 / 対象の数。除いた親 Issue は「対象外」の表に分け、その子 Issue の済 / 全体を添える |
| コメントの数 | 1 つ。先頭行の目印(`<!-- release-gate -->`)で始まる、Bot が書いたコメント(`GITHUB_TOKEN` で書くと `github-actions[bot]`)を探して上書きする。なければ作る。人が書いたコメントは上書きしない |
| 結果 | 成功で終える。終わっていない Issue があっても失敗させない。取得やコメントの失敗の扱いは、「取得やコメントに失敗したとき」 |
| 権限 | `pull-requests: write`(コメントの作成と更新)と `issues: read`(Issue の読み取り)だけ。リポジトリは取得しない |
| 必須チェック | `ci.yml` に含めない。Ruleset の必須ステータスチェックにも加えない([01-operations.md](01-operations.md) の「未設定」の表) |

コメントの見た目の例(抜粋)。

```
## リリースゲート

マイルストーン: v1.0.1

済 4 / 対象 6 件(未 2 件)

| Issue | タイトル | 領域 | 状態 |
| --- | --- | --- | --- |
| #17 | 【CORE】… | CORE | 未 |
| #19 | 【DOCS】… | DOCS | 済 |
```

- ゲートは PR のマイルストーンを見る。**リリース PR には、リリースするマイルストーンを設定する**(次の節)
- `main` 宛てのすべての PR で動く。`hotfix/*` の PR にも出るが、その PR のマイルストーンの Issue が出るだけで、リリースの確認には使わない。確認に使うのは、`develop` → `main` のリリース PR のコメント
- Issue の状態は、ゲートが動いた時点のもの。コメントの「更新」の時刻で、いつの内容か分かる

### リリース PR のマイルストーン

- 作るとき: `gh pr create --base main --head develop --milestone "<マイルストーン名>" …`(`…` は、ほかの引数)
- 作ったあと: `gh pr edit <PR 番号> --milestone "<マイルストーン名>"`。マイルストーンの変更で、ゲートが動く
- 付けないと、コメントは「マイルストーンが未設定」になる
- [03-release.md](03-release.md) の手順 1 の `gh pr create` には、`--milestone` がまだない。手順書への反映は未了(「未決」の節)。それまでは、上のコマンドで付ける

### 更新されるとき

- 更新されるのは、PR の作成・開き直し・コミットの追加・タイトルや本文の編集・マイルストーンの変更のとき。**Issue を閉じただけでは、更新されない**
- 最新にするには、Actions の `release-gate` の実行を再実行するか、PR のマイルストーンを付け直す。再実行しても、実行時点の PR のマイルストーンと Issue の状態を読み直す(起動したときのイベントの値は使わない)
- PR が競合しているあいだは、`pull_request` の workflow は動かない(GitHub の仕様)。競合を解消すると動く
- 同じ PR で 3 つ以上の実行が重なると、待機中の古い実行は取り消される(GitHub の仕様。失敗ではない)。最後の実行が、最新の状態を書く。チェック欄での見え方は、GitHub 上では未確認

### 取得やコメントに失敗したとき

想定した失敗は、`::warning::` を出して**成功で終える**(リリースを止めない)。想定外の失敗は、ステップが失敗として表示されるが、`continue-on-error: true` により、ジョブは成功のままにする(GitHub 上では未確認)。

| 場面 | 動き |
| --- | --- |
| Issue の取得に失敗(権限、API の障害など) | コメントは更新しない。前回の内容が残る |
| 既存のコメントの一覧の取得に失敗 | コメントが増えないよう、書かない |
| コメントの作成・更新に失敗 | 警告だけ。内容は、実行の画面のサマリ(Summary)に残る |
| fork からの PR | `GITHUB_TOKEN` が読み取り専用になる(GitHub の仕様)ため、取得はできるが、コメントは書けずに終わる。内容は、サマリで読める。このリポジトリのリリース PR は、同じリポジトリの `develop` から出すので、通常は起きない。fork の PR での実際の動きは、このリポジトリでは試していない |
| Issue が 100 件を超える | 100 件ずつ、最後まで読む。5000 件を超えると、警告を出して、コメントは更新しない |
| 次のページがあるのに、位置やページ情報を読めない | 最後まで読んだことにしない。警告を出して、コメントは更新しない |
| gh の呼び出しが固まる | ステップごとに 5 分(`timeout-minutes: 5`)で打ち切る。打ち切りも `continue-on-error` で、ジョブは成功のまま(GitHub 上では未確認) |
| コメントが長すぎる | コメントの上限(65536 文字)に収まるよう、本体を 60000 文字で切って、注記を付ける(行の途中では切らない)。切ったときは、後ろの表(「対象外」の表を含む)は出ない。先頭の件数と、末尾の「更新」の行は出る |

Issue とマイルストーンのタイトルは、人が書く文字列なので、コメントの Markdown が崩れないように整える。`|` `` ` `` `*` `_` `~` `[` `]` `<` `>` `&` `!` `$` `\` は、前に `\` を付けて、そのまま表示する(`$` は、数式として描画されないようにするため)。改行は空白にする。`@` の後ろにはゼロ幅スペースを入れ、@メンションの通知が飛ばないようにする。裸の URL と `#123` のような番号は、対処しておらず、自動リンクのまま表示される。

### 仕組み

| 取得するもの | 方法 |
| --- | --- |
| PR のマイルストーン | GraphQL の `pullRequest.milestone`(実行時点の値) |
| マイルストーンの Issue | GraphQL の `milestone.issues`(Issue だけを返す。REST の Issue 一覧は PR も含む)を、100 件ずつ |
| 親 Issue の判定 | `subIssuesSummary.total` が 1 以上 |
| コメント | REST の `issues/<PR の番号>/comments` を一覧し、`POST`(作成)か `PATCH`(更新) |

## 親 Issue と子 Issue の使い方

- GitHub のサブ Issue を使う
- **親 Issue は必須ではない**。親も子も持たない単独の Issue でよい
- 子 Issue を持つ親 Issue **だけ**が、ゲートの対象外になる。親 Issue の完了は、子 Issue の完了で決まるため、親は数えない。子 Issue と単独の Issue は、対象になる
- 子 Issue が 1 つでもあれば(開いていても閉じていても)、親として扱う。子でもあり親でもある Issue(孫がいる Issue)も、対象外になる
- 子 Issue は、**リリースするマイルストーンに付ける**。別のマイルストーンに付けると、ゲートの数に入らない(親の「対象外」の表に、子 Issue の済 / 全体は出る)。対象がすべて済でも、対象外の親 Issue に終わっていない子 Issue があるときは、件数の下に注意を 1 行出す
- 子の作り方、付け外しのコマンドは、スキル `issue-professional`(`.claude/skills/issue-professional/SKILL.md`)にある

## マイルストーンの命名と期間

- 名前は `v1.<半年ごと>.<2週ごと>`。2026-11-01 に開始し、最初は `v1.0.1`。2 週ごとに `v1.0.2`、`v1.0.3` と進む。`<半年ごと>` が `v1.1.x` に変わる日は未決(「未決」の節)
- **期限**は、マイルストーン自体の期限(`due_on`)に設定する
- **開始日**は、マイルストーンの説明欄に「開始 / 期限」で書く。例: `開始 2026-11-01 / 期限 2026-11-15`(`v1.0.1`)
- クローズ済みの過去の Issue は、マイルストーンに紐づけない。「過去」の範囲は未決(「未決」の節)。紐づけたクローズ済みの Issue は、ゲートで「済」に数える
- マイルストーンの一覧の取得と、名前の付け替えのコマンドは、スキル `issue-professional` にある

## 領域ラベル

- 領域ラベルは、`INFRA` / `BE` / `DOCS` / `CORE` の **4 種類**。タイトルのプレフィックス(`【INFRA】` など)と同じ。対象は [01-operations.md](01-operations.md) の「タイトルのプレフィックス」の表
- Issue には、プレフィックスと同じ領域のラベルを **1 つ**付ける
- ゲートのコメントの「領域」列に出る。この 4 種類以外のラベルは出さない。4 種類のラベルがない Issue は「なし」と出る
